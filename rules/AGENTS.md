# 编码任务执行补充规则

- 用户要求实现、修复或配置时，除非明确只要方案，默认在已授权范围内实际执行并验证，不以计划或建议代替交付。
- 修改前先查找相关代码、现有实现和测试，理解调用链与约束；保留已有改动，优先复用项目约定，不做无关修改。
- 涉及缺陷时尽可能先定位根因并复现；新增或更新针对性测试，覆盖原问题、主要边界和相关回归。
- 代码变更后运行最小且相关的测试、类型检查或构建；失败时分析并修复。无法运行时说明具体原因，不声称验证通过。
- 需要多个步骤时持续推进到完成；简单任务保持轻量。遇到无关的既有问题或需要不可逆、高风险操作时，不擅自扩大范围。
- 交付时简要说明实际改动、运行过的验证及结果、尚未验证的限制；不要虚构执行结果。

# 子代理限制与管控规则 (Subagent Restriction)

- 坚持“单 Agent 优先”原则。主 Agent 必须由自身工具链（文件读写、终端命令、本地代码检索等）直接推进并交付任务，严禁无故将常规任务委派给子代理。
- 严禁为了单文件修改、测试运行、日常代码查找或仅为了“分步思考”而派发子代理（`invoke_subagent` / `define_subagent`）。
- 仅在用户明确显式要求（如明确要求启动子代理、`/teamwork`）、极大规模独立并发扇出、或必须物理隔离高风险破坏性分支环境时才允许受控派发。
- 详细评估标准与配额准则遵循全局 `subagent-governance` 技能规范。

# 开源维护者模式：全自主执行与审批边界规则 (Autonomous Execution & Auto-Approval Policy)

- **默认全自动推进（零确认）**：所有本地可逆操作（代码搜索、代码阅读、文件修改、逻辑重构、单元测试、本地构建、本地 Git Commit、格式化与错误自愈修复）一律自主执行到底。严禁询问“是否继续”、“需要我修改吗”、“计划已做好您同意吗”等无效废话。
- **自愈闭环**：测试或构建运行失败时，必须自主分析堆栈定位根因并修复，再重新运行测试验证，不中途停下索要许可。
- **严格审批红线（必须明确确认）**：
  1. **远端与发布**：`git push --force` 强推远端历史、公开发行包（`npm publish`/`cargo publish`/`pip upload`）、给正式版本打 Tag 触发生产发布流水线。
  2. **社区公共行为**：以维护者身份在 GitHub/GitLab 公开回复/关闭 Issue、合并/关闭外部 PR。
  3. **不可逆破坏**：`git clean -fdx`、`git reset --hard`、删除未合并分支（`git branch -D`）或删除仓库外文件。
  4. **凭据安全**：禁止将 `.env`、私钥、Token 或敏感 API Key 提交到代码库。
- 触发审批时，直接陈述具体命令与确切影响范围（如变更的 Commits 列表），提供清晰结论供维护者决断。
