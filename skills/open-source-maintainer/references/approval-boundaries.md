# 开源项目操作审批边界与命令对照表 (Approval Boundaries)

本文档罗列开源项目日常开发中的具体命令归类，明确哪些必须全自动执行，哪些必须请求维护者审批。

---

## 1. 命令分级对照表

| 场景分类 | 命令示例 | 审批级别 | 行为规范 |
| :--- | :--- | :---: | :--- |
| **代码搜索与检查** | `rg "pattern"`, `git status`, `git log` | 🟢 **全自动** | 直接执行，输出必要摘要。 |
| **测试与校验** | `npm test`, `pytest`, `cargo check`, `eslint` | 🟢 **全自动** | 自动执行并解析结果；报错则自主修复。 |
| **代码格式化** | `prettier --write`, `cargo fmt`, `black .` | 🟢 **全自动** | 直接执行并校验格式。 |
| **本地提交** | `git add .`, `git commit -m "..."` | 🟢 **全自动** | 规范编写 commit message，直接提交本地。 |
| **本地新分支** | `git checkout -b feature/xxx` | 🟢 **全自动** | 为新任务隔离开发环境，直接创建。 |
| **Scratch 验证** | 编写临时脚本验证特定库的行为 | 🟢 **全自动** | 在 scratch 目录创建并运行。 |
| **普通远端推送** | `git push origin <feature-branch>` | 🟡 **已授权时自动** | 若用户已明确要求“推到 GitHub”，直接执行。 |
| **强制覆盖推送** | `git push --force`, `git push -f` | 🔴 **严加审批** | **必须向维护者确认**，说明覆盖风险。 |
| **主分支发版推送** | `git push origin main` (生产分支) | 🔴 **需确认** | 列出本次提交的 commits 概要供审查。 |
| **公开发行包** | `npm publish`, `cargo publish`, `twine upload` | 🔴 **严加审批** | **必须向维护者确认**，核对版本号与包名。 |
| **GitHub PR 合并** | `gh pr merge`, REST API merge | 🔴 **严加审批** | **必须向维护者确认**，展示 PR 变更审查结论。 |
| **彻底清空工作区** | `git clean -fdx`, `git reset --hard` | 🔴 **严加审批** | **必须向维护者确认**，避免丢弃未追踪改动。 |
| **删除分支/标签** | `git branch -D`, `git push origin :tag` | 🔴 **严加审批** | **必须向维护者确认**。 |

---

## 2. 避免无意义反问的准则

维护者通常在快速审查代码和调度架构，以下反问句式被列为**劣质沟通，严禁使用**：
- ❌ “我发现测试挂了一个用例，您希望我继续修复它吗？” -> （应自行分析并修复）
- ❌ “方案已经制定完毕，请问我可以开始修改代码了吗？” -> （应直接进入编码阶段）
- ❌ “代码修改已经完成，需要为您运行测试验证吗？” -> （必须直接运行相关测试）
- ❌ “我已经修改好文件，需要我为您做 git commit 吗？” -> （在本地完成高质量 commit 即可）
